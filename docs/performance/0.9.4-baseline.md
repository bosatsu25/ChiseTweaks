# ChiseTweaks 0.9.4 Performance Acceptance

この手順は実機Prismで取得した値だけをperformance evidenceとして扱います。CI runnerのwall-clock値をゲーム内FPSの代用にはしません。

## 必須scenario

同一PC・同一instance・同一world/位置・同一描画条件で、各scenarioを最低3回測定します。

| Scenario | 内容 |
| --- | --- |
| `chise-absent` | ChiseTweaksを読み込まないcontrol |
| `chise-all-off` | ChiseTweaksあり、11 runtime featureはOFF |
| `analyzers-on` | Lava Source + Ancient Debris Analyzer ON |
| `highlights-on` | 主なHighlightを同時ON |
| `maximum-supported-load` | 公開上限内でAnalyzer / Highlightを最大負荷寄りに設定 |

0.9.3をbaseline、0.9.4 candidateをcandidateとして比較します。`environment_id`は同じ測定環境を表す匿名ラベルにし、ユーザー名やlocal pathを入れないでください。

## Template生成

```bash
python scripts/performance_evidence_template.py <evidence-dir> --environment-id chise-test-rig-a
```

10個のCSV（5scenario × baseline/candidate）を生成します。既存ファイルは上書きしません。

各CSVは次のmetricを持ちます。

- `startup_ms`
- `p50_frametime_ms`
- `p95_frametime_ms`
- `p99_frametime_ms`
- `heap_mib`
- `allocation_mib_s`
- `render_thread_cpu_pct`
- `average_fps`

空欄の3行を実測値で埋めます。3回より多く測定しても構いません。

## 比較

scenarioごとにbaseline/candidateを指定します。

```bash
./gradlew comparePerformanceEvidence \
  -PperformanceBaseline=<baseline.csv> \
  -PperformanceCandidate=<candidate.csv>
```

JFRも取得した場合:

```bash
./gradlew comparePerformanceEvidence \
  -PperformanceBaseline=<baseline.csv> \
  -PperformanceCandidate=<candidate.csv> \
  -PperformanceBaselineJfr=<baseline.jfr> \
  -PperformanceCandidateJfr=<candidate.jfr>
```

## Acceptance budgets

現在のpolicyでは、少なくともP50/P95/P99 frametime、heap、average FPSに3 samplesずつ必要です。主な許容回帰は以下です。

- startup: 15%
- P50 frametime: 8%
- P95 frametime: 10%
- P99 frametime: 15%
- heap: 10%
- allocation rate: 15%
- render-thread CPU: 10%
- average FPS: 10%低下まで

CLIが `performance_acceptance=PASS` を返したscenarioのみ合格です。

## CIで自動化する範囲

CIでは実GPUのFPSを測りません。その代わり、次の決定的なperformance contractを毎回監査します。

- production `Thread.sleep` 禁止
- Resource Pack reloadのblocking wait禁止
- reload APIの呼出箇所をcoalescing controllerへ限定
- Analyzerが未ロードchunkを強制loadしないこと
- Ancient Debris bootstrap / validation / cache上限を固定
- ResourceReloadCoordinatorを10,000 cycle回してstuckしないこと
- Ancient Debrisを1時間相当のtick数でbudget simulationすること
- runtime JAR容量を0.9.3の検証済みbaselineからの増加量で監視

この自動監査がPASSしても、実機5scenarioの測定がなければ **0.9.4 performance acceptance = NOT EXECUTED** です。
