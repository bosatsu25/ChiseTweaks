# ChiseTweaks Versioning Policy

ChiseTweaks uses Semantic Versioning for the product version and keeps Minecraft compatibility in SemVer build metadata.

## Format

`MAJOR.MINOR.PATCH+mc<Minecraft version>`

Example: `0.8.0+mc26.1.2`

The SemVer core is `0.8.0`. The `+mc26.1.2` suffix identifies the Minecraft compatibility target and does not change SemVer precedence.

## When to increment

- **PATCH** (`0.8.0` -> `0.8.1`): bug fixes, performance tuning, QA/CI hardening, documentation, or UI polish that does not add a user-facing capability or intentionally break a contract.
- **MINOR** (`0.7.7` -> `0.8.0`): backward-compatible user-facing functionality, a new feature/toggle/analyzer, or a substantial new workflow capability. Ancient Debris Analyzer is therefore released as `0.8.0`.
- **MAJOR** (`0.x.y` -> `1.0.0`, then `1.x.y` -> `2.0.0`): an intentional incompatible configuration/runtime/API contract, removal requiring migration, or the first declared stable 1.0 contract.

Although SemVer permits broad changes before 1.0, ChiseTweaks intentionally follows these rules during `0.x` development so release meaning stays predictable.

## Release rules

1. Every official release must increase the SemVer core. Reusing the same version for a different main commit is forbidden.
2. Normal CI never creates a tag or GitHub Release. It remains read-only and verifies pull requests and `main` pushes.
3. A successful `push` CI run on `main` automatically triggers **Official Release**. Pull-request CI and manually dispatched CI runs never publish.
4. Official Release checks out the exact commit SHA verified by the successful CI run. If `main` has already advanced, the stale result is skipped instead of publishing an older commit.
5. Release type is inferred from the exact SemVer delta. Only one-step PATCH, MINOR, or MAJOR increments are accepted when a previous release version exists.
6. If the same version already has a GitHub Release, no duplicate Release is created. A conflicting standalone tag is treated as an error rather than overwritten.
7. The only user-uploaded Release asset is the installable runtime JAR.
8. `-sources.jar`, QA JSON, checksums, reports, ZIP files, and tarballs are never uploaded as ChiseTweaks Release assets.
9. After publication, the workflow verifies the Release asset count, file name, GitHub digest, tag target SHA, downloaded JAR SHA-256, `fabric.mod.json`, Minecraft/Fabric/Java constraints, and the client-only contract.
10. GitHub automatically exposes source-code `.zip` and `.tar.gz` links for every Git tag/Release. Those are generated by GitHub itself and cannot be disabled by the ChiseTweaks workflow; they are not mod artifacts and must not be installed in Prism Launcher.

## Release checklist

- Update `mod_version` in `gradle.properties` according to this policy before merging the release-worthy change.
- Merge through the normal CI quality gate.
- Let the `main` push CI complete successfully.
- **Official Release** then rebuilds and audits that exact CI-verified commit automatically.
- Confirm that GitHub Releases contains one uploaded mod asset: `chise-tweaks-<version>.jar`.
- Use the SHA-256 shown in the concise Release notes when independently checking the downloaded JAR.
